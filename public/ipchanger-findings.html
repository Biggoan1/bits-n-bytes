IPChanger & the Network Configuration Operators problem

Everything we tried to let a non-admin field tech change a PC's IP on a hardened Windows 11 box — why most of it failed, what actually works, and the one registry value that was the real culprit.

The one-paragraph answer

The blocker was never the Network Configuration Operators (NCO) group, netsh, or the "Network Connections" Group Policy node. It was UAC token filtering, which depends on the logon type — and on hardened boxes it was compounded by a single registry value, ConsentPromptBehaviorUser = 0 ("automatically deny standard-user elevation").

NCO does grant the IP-change right, but UAC strips NCO out of interactive logon tokens. It survives intact in network and batch logons. So the same account that fails at the desktop succeeds over SSH or from a scheduled task. The fix on the affected machine was ConsentPromptBehaviorUser 0 → 3. Three viable app architectures fall out of this: a batch-logon broker, a user-mode DHCP self-assign, and JEA.

01 The problem

Field technicians — non-technical staff, deliberately given zero local admin — need to set a laptop's IPv4 to talk to network equipment on an isolated bench link. Privileged tasks are meant to use a separate xID account, which is also not a local admin. The target image is Windows 11 25H2 under a Microsoft/CIS-style hardening baseline. The tool is IPChanger, a PowerShell WinForms app compiled with ps2exe.

The obvious answer — put the xID in Network Configuration Operators, the built-in group Microsoft ships precisely so non-admins can change TCP/IP — didn't work interactively. Understanding why took the whole investigation below.

02 Core mechanism — logon type decides everything

NCO's SID (S-1-5-32-556) sits on UAC's list of "administrator-equivalent" groups, alongside Backup Operators and Power Users. When UAC builds a filtered token, those groups are set to deny-only or dropped entirely. Whether filtering happens is decided by the logon type:

Interactive logon

type 2 — console, RDP, runas/CreateProcessWithLogonW

UAC builds a filtered token. NCO is deny-only / absent — the app logged ncoInToken=False.

✕ ncpa.cpl & netsh both fail

Network & batch logon

type 3 — SSH/SMB/PS-remoting · type 4 — scheduled task

No UAC filtering. whoami /groups shows NCO as an "Enabled group".

✓ netsh changes the IP, exit 0

This single fact explains everything downstream: every early "it works!" result was measured over SSH (a network logon), and John's original desktop failure was the same root cause — not a separate ncpa.cpl quirk.

05 The GPO red herring — NC_LanChangeProperties

A fair question came up: could the User Config → Administrative Templates → Network → Network Connections policies be an independent cause? On Windows 11 the only policy in that node whose text names NCO is NC_LanChangeProperties ("Prohibit access to properties of components of a LAN connection") — Microsoft says enabling it "prohibits Network Configuration Operators from accessing connection components." We tested it directly.

Condition (as x_Winston, NCO enabled)netsh set address source=static
Policy not setexit 0 — applied
Policy = 1, planted in the live hive & confirmed visible in sessionexit 0 — applied

Identical. The policy governs only the ncpa.cpl GUI "Properties" button (netshell); netsh.exe and every scripted path ignore it. We also confirmed the hardening baseline never sets it, and a standard user can't self-set it (HKCU\Software\Policies is admin/GPO-only). The Network Connections GPO node is ruled out.

06 Root cause & the real fix

On the affected machine, standard-user elevation was configured to fail silently. Instead of a credential prompt, users got an error and nothing else — the classic symptom of:

# HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\System
ConsentPromptBehaviorUser = 0   ← "Automatically deny elevation requests"
                          → 3   ← "Prompt for credentials" (Windows default) = FIXED

# GPO: Computer Config → … → Security Options →
# "User Account Control: Behavior of the elevation prompt for standard users"

Why 0 → 3 fixed it

At 0, the standard-user elevation path is auto-denied before NCO can even be evaluated — an error with no prompt. At 3 (or 1, prompt on the secure desktop) the flow proceeds and the NCO-backed change resolves. Note the tension: CIS/STIG baselines recommend 0, so a hardened gold image ships pre-broken for this workflow. In the lab baseline we moved 0 → 1 and set TypeOfAdminApprovalMode 2 → 1 (Administrator Protection off, classic Admin Approval Mode).

07 Field notes & gotchas

  • netsh static is additive. Setting a static address keeps the DHCP lease and adds the manual one. set source=dhcp errors when DHCP is already on — the correct revert is delete address.
  • Gateways leave a route. Setting a gateway leaves a default route after the address is deleted. Either skip the gateway (same-subnet gear needs none) or delete route explicitly.
  • SeBatchLogonRight is stripped by the baseline. Only Administrators/Backup Operators/Perf Log Users get it. The broker needs NetOps granted "Log on as a batch job" via GPO — this was the 267011 "task never ran" failure.
  • CIM/WMI is denied to NCO. Enumerate adapters with .NET NetworkInterface, never Get-NetAdapter.
  • Testing hazard. netsh add/set address on a machine's only DHCP NIC can disable DHCP → APIPA (169.254.x) → cut remote access. Always test on a second NIC; recover via the hypervisor console (… set address source=dhcp).
  • Elevation ≠ NCO. A non-admin can never UAC-elevate, full stop — only local Administrators can. NCO grants the capability, not the ability to elevate.

09 Addendum — the tool put forward as a counter-example

"Simple IP Config 2.8 works every time in dev." We pulled it apart to see whether it beats the constraint or just avoids it. It's an AutoIt v3 (EA06) compiled, unsigned executable; we extracted its 234 KB script. It confirms the findings above rather than contradicting them.

How it elevates — we looked for a SYSTEM broker; there isn't one

A reasonable suspicion was that it smuggles privilege via a scheduled task or a SYSTEM helper. It doesn't. The entire 234 KB script spawns exactly one worker process:

$IPID = Run( @ComSpec & " /k " & $cmd, "", @SW_HIDE, ... )   ; $cmd = netsh interface ip set address …

That is a plain Run() — no username, no password, no "runas" verb — so the child cmd/netsh simply inherits the app's own token. The app is elevated for one reason only: #requireadmin on line 1, which relaunches the whole GUI at high integrity. So netsh runs as the logged-on admin user, not SYSTEM. The async queue wrapped around it (_AsyncNewCmd) is just a stdout poller so the window doesn't freeze — not a privilege path.

The token APIs that do appear in the binary (AdjustTokenPrivileges, ImpersonateSelf, SeDebugPrivilege) are stock AutoIt library includes (Security.au3 / Memory.au3) dragged in as dependencies and never called on the apply path. Net: nothing in it can bridge a missing admin token — there is no SYSTEM fallback, so on a non-admin box it just fails.

Verdict

It is approach #1 (self-elevate) in an AutoIt wrapper. "Works every time in dev" means the dev user is a local admin (and/or UAC is relaxed), so #requireadmin gets a full token and netsh runs elevated. Drop the same exe on a non-admin, hardened prod image and it hits the identical UAC wall this whole investigation is about — and its WMI enumeration adds a second, independent failure. It never solves the hard part; it assumes admin, which is invisible when everyone in the dev room already has it.

So it isn't a counter-example — it's a confirmation. Tellingly, the one part of it that needs no admin is its netsh apply path, which is precisely the mechanism our non-admin designs are built on.

And in the production environment it almost certainly never runs at all: an unsigned AutoIt EA06 binary is denied by application allowlisting (Airlock) before privilege even enters the picture — no trusted publisher, not on the allowlist, and an interpreter/packer profile that EDR is built to flag. "Works every time in dev" is measuring a machine with allowlisting off and the user holding admin — the two conditions prod is designed to remove.
